## 4. Step 1: eliminate the session-state lost-wakeup race

### Problem

`SessionState::wait()` currently checks the stored terminal result and only then creates and awaits a `Notify` future. `SessionState::finish()` can set the result and call `notify_waiters()` between those two operations. Because `notify_waiters()` does not retain a permit for a future waiter, `wait()` can then sleep indefinitely even though the session has already terminated.

### Required change

Choose one of these implementations:

1. Keep `Notify`, but create the `notified()` future before checking the result on every loop iteration.
2. Replace the result-plus-`Notify` combination with a Tokio `watch` channel carrying terminal state.

Prefer the smallest correct change unless a later lifecycle requirement materially benefits from `watch`.

Preserve these semantics:

- The first terminal result wins.
- Any number of current or future waiters receive that result.
- Calling `wait()` after the session has already terminated returns immediately.
- Successful and failed termination are both observable.

### Tests

Add deterministic tests for:

- A waiter registered before `finish()`.
- `finish()` completed before `wait()` begins.
- Several simultaneous waiters.
- Repeated `wait()` calls after completion.
- Preservation of an error result.

Wrap waits in short Tokio timeouts so a regression fails rather than hanging the suite.

### Completion criteria

- No notification can be lost between checking state and waiting.
- All lifecycle tests pass repeatedly.
- Existing HTTP/2-over-WebSocket tests remain unchanged and pass.

### Result

Complete. `SessionState::wait()` registers its `Notify` future before checking
terminal state, and lifecycle tests cover pre- and post-completion waits,
multiple waiters, repeated waits, and error preservation. Focused, crate, and
workspace tests pass. Strict Clippy still has the unrelated findings listed in
Step 10.

## 5. Step 2: validate related buffer limits

### Problem

The adapter can generate an outgoing binary message of `bridge_buffer_size` bytes. Configuration currently allows that value to exceed `max_message_size` or `max_frame_size`, causing two peers with matching configuration to reject messages generated by the adapter itself.

### Required change

Extend `Config::validate()` to require:

```text
bridge_buffer_size <= max_message_size
bridge_buffer_size <= max_frame_size
```

Retain the existing checks for zero sizes and write-buffer ordering.

Consider whether `max_write_buffer_size` must also be large enough for one complete outbound message plus Tungstenite framing. Follow Tungstenite's documented constraint rather than inventing an arbitrary safety margin.

### Tests

Test:

- Default configuration is valid.
- Equality with message and frame limits is valid.
- A bridge buffer one byte above the message limit is rejected.
- A bridge buffer one byte above the frame limit is rejected.
- Existing zero-size and write-buffer checks remain effective.

### Completion criteria

- Matching peers never reject a bridge-generated message solely because of their shared configured limits.
- Every invalid relationship returns a specific configuration error before a connection is opened.

### Result

Complete. `Config::validate()` now requires the bridge buffer to fit within
both the maximum message and frame sizes. Tests cover defaults, equality,
one-byte violations, zero sizes, and write-buffer ordering. The existing
Tungstenite write-buffer relationship remains unchanged. Crate and workspace
tests pass; strict Clippy still has the Step 10 findings.

## 6. Step 3: test actual message-to-byte-stream adaptation

### Problem

The current test named `binary_messages_form_one_continuous_byte_stream` communicates directly between two WebSocket endpoints. It confirms WebSocket message behavior but never runs the bridge or reads from its Tokio byte-stream side.

### Required change

Replace it with a real adapter test:

1. Create an in-memory WebSocket pair.
2. Create a bounded Tokio duplex pair.
3. Run `bridge()` between one WebSocket and one duplex endpoint.
4. Send several binary WebSocket messages with deliberately different sizes.
5. Read the combined bytes from the other duplex endpoint using read sizes that do not align with the message boundaries.
6. Assert byte-for-byte equality with the concatenated payload.

Add the reverse direction:

1. Write a continuous byte sequence to the duplex endpoint using uneven writes.
2. Read binary WebSocket messages from the peer.
3. Concatenate their payloads.
4. Assert byte-for-byte equality with the original stream.

Tests must not assume that one byte-stream write produces one WebSocket message or that one read corresponds to one message.

### Completion criteria

- The production `bridge()` function is exercised.
- Both directions preserve every byte and its order.
- Tests explicitly cross WebSocket-message and byte-read boundaries.

### Result

Complete. The direct WebSocket endpoint test was replaced with production
`bridge()` tests in both directions. They use message boundaries and byte
reads/writes that do not align, and all reads are time-bounded. Crate and
workspace tests pass; strict Clippy still has the Step 10 findings.

## 7. Step 4: prove independent progress under backpressure

### Problem

The updated bridge has independent reader, writer, and WebSocket-reader tasks. This addresses the earlier single-loop blocking design, but it is not yet tested under deliberate backpressure.

### Required change

Add controlled tests using small duplex capacities and short timeouts.

#### Scenario A: WebSocket to local is stalled

1. Fill the local inbound duplex capacity and stop reading it.
2. Cause `websocket_to_local` to block on `write_all()`.
3. Write bytes in the opposite direction from the local HTTP/2 side.
4. Confirm those bytes still reach the remote WebSocket peer.

#### Scenario B: local to WebSocket is stalled

1. Prevent or severely delay consumption from the remote WebSocket side.
2. Fill the bounded writer-command and WebSocket write capacity.
3. Send a message from the remote WebSocket toward the local duplex side.
4. Confirm it can still be delivered without waiting for the outgoing application data to drain.

If the WebSocket implementation makes Scenario B difficult to control deterministically in memory, introduce test-only synchronization around the sink rather than relying on timing or very large allocations.

### Completion criteria

- Backpressure in one data direction does not prevent useful progress in the other.
- Tests are deterministic and bounded by timeouts.
- No unbounded queue or detached task is introduced to make the tests pass.

### Result

Complete. Controlled small-capacity duplex tests now stall each direction in
turn and verify that the opposite direction still makes progress. A test-only
write wrapper signals actual `Pending` writes, keeping the scenarios
deterministic without changing production buffering. Crate and workspace tests
pass; strict Clippy still has the Step 10 findings.

## 8. Step 5: make close and shutdown bounded

### Problem

`close_websocket()` sends a close command and then waits indefinitely for the writer task to acknowledge it. If the WebSocket sink is permanently blocked, the bridge may never finish closing.

### Required change

Add a configurable graceful-close deadline or an internal conservative timeout. Prefer making it part of `Config` if callers need to tune it for different networks.

Required behavior:

- Attempt an orderly WebSocket close.
- Wait only for the configured deadline.
- Treat expiration as permission to tear down the local bridge rather than wait forever.
- Ensure the bridge supervisor aborts and joins remaining pump tasks.
- Do not convert an otherwise clean local EOF into an unbounded shutdown.
- Decide and document whether close-timeout expiry is a clean termination or a transport error.

The close command acknowledgement must remain bounded behind the writer queue. Control traffic must not be placed in an unbounded priority bypass.

### Tests

Test:

- Normal close receives acknowledgement and completes cleanly.
- A deliberately blocked writer reaches the deadline and terminates.
- Local EOF triggers the close path.
- Remote close shuts down the local byte-stream writer.
- No pump remains active after the bridge returns.

Use paused Tokio time where practical to avoid slow wall-clock tests.

### Completion criteria

- Every close path has a finite completion time.
- Normal closes remain graceful.
- Stalled peers cannot keep a bridge task alive indefinitely.

### Result

Complete. `Config::close_timeout` bounds the queued close command and
acknowledgement, and local write-half shutdown is bounded as well. Timeout
expiry tears down the bridge cleanly; the close command remains behind the
bounded writer queue. `SendAfterClosing` is treated as an already-completed
orderly close. Tests cover normal local EOF, stalled writers, remote close,
local EOF propagation, and bridge completion. Crate and workspace tests pass;
strict Clippy still has the Step 10 findings.

## 9. Step 6: test failure, cancellation, EOF, and cleanup

### Required scenarios

Add bridge tests for:

- WebSocket read failure.
- WebSocket write failure.
- Local byte-stream read failure or EOF.
- Local byte-stream write failure.
- Text-message protocol error.
- Oversized incoming message.
- Dropping the HTTP/2/client side of the duplex stream.
- Aborting the outer bridge future.

For every scenario, verify:

- The bridge returns the expected success or error category.
- Other pump tasks are cancelled.
- Every spawned task is joined or aborted and drained.
- The peer observes close, EOF, or failure rather than hanging.
- No later bytes appear after termination.

### HTTP/2 cancellation scenario

Over a real WebSocket-backed HTTP/2 session:

1. Open a response stream large enough to remain active.
2. Begin receiving data.
3. Drop or reset that stream.
4. Confirm the server observes cancellation and stops producing its body.
5. Confirm another stream completes over the same connection.

### Completion criteria

- Transport-level failure does not leave background work alive.
- HTTP/2 stream cancellation does not close the WebSocket or unrelated streams.
- Failure behavior is covered by time-bounded tests.

### Result

Complete. Time-bounded tests cover WebSocket and local read/write failures,
text protocol errors, oversized messages, local EOF, dropped local streams,
outer bridge cancellation, and blocked-task cleanup. A real WebSocket-backed
HTTP/2 test confirms that cancelling a streaming response resets only that
stream and another stream still completes on the same connection. Crate and
workspace tests pass; strict Clippy still has the Step 10 findings.

## 11. Step 8: settle the public server API

### Problem

The crate currently exposes both:

- Generic `serve(websocket, config, start_server)` for any byte-stream protocol.
- HTTP/2-specific `ServerSession` and `server_session()`.

The deployed home application still uses generic `serve()`, while the crate is intended to be specifically HTTP/2 over WebSocket.

### Decision

Prefer the HTTP/2-specific API for the extracted crate:

```text
connect / connect_client          -> ClientSession
accept_server / server_session    -> ServerSession
```

Migrate the Journey home application to `ServerSession`. Keep the raw bridge private.

Remove generic `serve()` and `ServeError` unless a concrete non-HTTP/2 consumer justifies retaining them. If retained, document them as an intentionally supported lower-level API and reconsider whether the crate's public scope is still accurately named.

### Migration behavior

The home application should:

1. Establish its outbound bounded, subprotocol-negotiated WebSocket.
2. Create `ServerSession` over it.
3. Accept HTTP/2 requests from the session.
4. Pass each request and responder to Journey's existing request handler.
5. Observe terminal session state and reconnect through the existing outer loop.

### Completion criteria

- The public client and server APIs are symmetric.
- The deployed applications use those APIs.
- No Journey route or body policy moves into the transport crate.
- Obsolete generic transport API is removed or explicitly justified.

### Result

Complete. `journey-websocket` now exposes the symmetric HTTP/2-specific
`connect`/`connect_client` and `accept_server`/`server_session` APIs while the
raw bridge remains private. The generic transport `serve()` and `ServeError`
were removed. `journey-home` now establishes the bounded, negotiated outbound
WebSocket, creates a `ServerSession`, dispatches accepted requests to the
existing Journey handler, observes terminal session state, and reconnects
through its existing loop. Journey routing and response policy remain in the
application crate.

## 12. Step 9: tighten Journey response backpressure

### Problem

The gateway currently releases HTTP/2 receive capacity immediately before yielding a chunk to Axum. This allows the inner sender to advance as soon as the chunk enters the public HTTP stack rather than when downstream requests the next chunk.

### Required change

Replace the simple unfold adapter with a body/stream state that:

1. Stores the byte count of the last yielded HTTP/2 DATA chunk.
2. Releases that capacity when polled for the next chunk.
3. Polls the inner response for another DATA frame only after releasing the preceding one.
4. Drops the inner response stream when the public response is cancelled.

This keeps at most one explicitly tracked inner DATA chunk ahead of downstream demand, in addition to bounded buffers owned by Hyper and the operating system.

### Tests

Verify:

- Capacity is not released merely because a chunk was received.
- Polling for the next chunk releases the previous chunk's capacity.
- Stopping after one chunk prevents continued inner progress beyond configured windows.
- Dropping the public body resets or drops the inner HTTP/2 stream.

### Completion criteria

- Public-client backpressure propagates predictably to inner HTTP/2 flow control.
- The gateway never collects a complete media object.
- Cancellation stops forwarding promptly.

### Result

Not completed.
